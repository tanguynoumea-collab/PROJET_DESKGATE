## Summary

Les cinq findings se ferment par des changements petits et localisés, sans dépendance ni migration de schéma. Le point structurant est que `data` est déjà persisté dans `jobs.result_json` (`engine.py:547-550`) mais lu par personne ; il suffit de l'exposer par les **deux** seuls constructeurs de vue (`core/payload.build_callback` et `jobs.job_view`, tous deux font `result.get("summary")`/`result.get("artifacts")`), et de généraliser le repli `_cap_summary` à `data`.

Recommandation de forme : clé `data` **toujours présente** (objet `{}` si vide) entre `summary` et `artifacts` ; au-delà du plafond, `data` devient `{"path": "<chemin conteneur>/data.json", "truncated": true}`, exactement le motif déjà utilisé par `summary` ; le fichier `data.json` est écrit par l'engine à la fin de la tâche. La rétention se fait **sans migration** : une commande manuelle `deskgate purge --older-than-days N` qui remplace `$.data` par `{"purged": true}` (SQL `json_set`, vérifié sur SQLite 3.50.4) pour les tâches terminées dont le rappel est final. Piège majeur découvert : `parse_constant` seul **ne suffit pas** pour NaN/Infinity, car `1e999` est converti en `inf` par `float()` sans passer par `parse_constant` ; il faut aussi `parse_float`.

**Primary recommendation :** faire dans cet ordre : (1) tests de caractérisation P-01/P-02, (2) sender P-01, (3) frontière NaN P-02 (avec `parse_float`), (4) contrat `data` (payload + job_view + engine `_cap_result`), (5) purge, (6) documentation. Les plans 1-3 sont indépendants ; le plan 4 doit précéder 5 et 6.

### Décision 1 — Forme exacte de `data` (DS-ARCH-1)

Recommandation (une seule option) :

```jsonc
// Cas normal (tient sous le plafond)
{ "job_id": "...", "capability": "mcp.call", "status": "succeeded", "duration_s": 3.2,
  "summary": { "server": "s", "tool": "t", "is_error": false },
  "data":    { "structured_content": {...}, "content": [...] },
  "artifacts": [], "error": null }

// Repli (corps > 1 Mio) : data déporté
  "data": { "path": "/data/travail/<job_id>/data.json", "truncated": true }

// Échec / annulé / timeout / interrupted : "data": {}
```

Choix et preuves :
- **Clé toujours présente, `{}` si vide** (pas `null`, pas absente) : c'est le motif de `summary` (`{}` par défaut, `payload.py:54`) ; le nœud n8n et les expressions `$json.body.data.x` ne cassent pas. Ordre des clés : `job_id, capability, status, duration_s, summary, data, artifacts, error`.
- **Marqueur = `{"path", "truncated": true}`** : strictement le format de `summary` (`engine.py:571`, test `tests/fs/test_engine_summary_cap.py:62`). Un seul vocabulaire à documenter. Le chemin passe par `host_to_container` (réutiliser `_write_summary` généralisé en `_write_json_file(cur, name, obj)`).
- **Pas d'entrée dans `artifacts`** (écart assumé avec le défaut du CONTEXT, qui laisse le choix) : `artifacts` contient des fichiers déclarés par le plugin, validés par `validate_artifact_path` ; `summary.json` n'y figure pas non plus. Y ajouter `data.json` créerait deux manières de retrouver le fichier. Si le planner préfère le défaut CONTEXT, c'est une ligne en plus (`{"kind": "data", "path": ...}`) sans autre impact.
- **Nom : `data.json`**, écriture atomique `.tmp` + `fsync` + `os.replace`, identique à `_write_summary` (`engine.py:581-601`).
- **Ordre de repli quand tout est gros** : (a) mesurer le corps complet ; (b) si > plafond, déporter `data` seul ; (c) remesurer ; (d) si encore > plafond, déporter aussi `summary`. Une boucle de deux étapes dans une méthode renommée `_cap_result`. Le dernier recours existant `payload.minimal` (troncature à la volée, 413) doit aussi remplacer `data` : `{**body, "summary": {"truncated": True}, "data": {"truncated": True}}`.
- **Échec d'écriture** (`OSError`) : mêmes marqueurs dégradés que summary : `{"truncated": True, "error": "data_write_failed"}`.
- **Un seul calcul** : le repli est décidé dans `_evaluate` et figé dans `result_json` ; `build_callback` et `job_view` ne font que relire. Garantit la même forme rappel/GET. Ajouter un helper pur commun dans `core/payload.py` (ex. `result_parts(result_json) -> (summary, data, artifacts)`) appelé par `build_callback` ET `job_view` pour qu'un oubli futur ne désynchronise pas les deux (`jobs.py` importe déjà `core.payload.duration_s`).

Après modification de `build_callback`, la mesure inclut `data` automatiquement ; vérifier que le test `test_borne_reelle_un_mio` (summary de `RESULT_MAX_BYTES-100`) reste vert (summary seul remplit déjà le plafond → repli du summary, `data` vide donc intact).

### Décision 2 — Rétention (DS-SCAL-1)

Recommandation : **`data` reste dans `jobs.result_json`** (pas de colonne séparée, pas de migration), borné à 1 Mio par construction (cf. plus haut), plus une **commande manuelle** :

`deskgate purge [--older-than-days N]` (défaut 30), sans toucher à `runner.toml`.

Justification manuel vs démarrage :
- Une purge au démarrage supprime des données silencieusement et en écriture lors de la phase critique de recovery (`runtime.py:180-221`) ; elle ajoute un cas d'échec au démarrage. Une commande explicite est testable, journalisable et réversible par non-exécution.
- Pas de clé de config : pas d'impact sur `core/config.py`, `runner.example.toml` ni `tests/unit/test_runner_example.py`.
- Limite assumée : « borné » = 1 Mio/tâche par construction + purgeable à la demande ; pas de purge automatique (cette automatisation, avec rétention d'audit et dossiers de tâche, reste en 999.2).

Fonction store (nouvelle, `store.py`), dans `tx(conn)` :

```python
def purge_data(conn, *, older_than: datetime) -> int:
    """Remplace `$.data` par {"purged": true} pour les tâches terminées dont le rappel est final."""
    with tx(conn):
        cur = conn.execute(
            "UPDATE jobs SET result_json = json_set(result_json, '$.data', json('{\"purged\":true}')) "
            "WHERE result_json IS NOT NULL AND finished_at < :cutoff "
            "AND status IN ('succeeded','failed','timeout','cancelled','interrupted') "
            "AND id IN (SELECT job_id FROM callbacks WHERE state IN "
            "('delivered','delivered_duplicate','abandoned_stale','abandoned_rejected','abandoned_exhausted')) "
            "AND json_type(result_json, '$.data') = 'object' "
            "AND json_extract(result_json, '$.data') NOT IN ('{}', '{\"purged\":true}')",
            {"cutoff": iso(older_than)},
        )
        return cur.rowcount
```
(Utiliser `CALLBACK_FINAL_STATES` pour construire la liste ; le SQL ci-dessus a été validé en essai local sur SQLite 3.50.4 : ligne avec `data` réécrite, ligne déjà purgée et ligne sans `data` intactes.)

- **Idempotente** (re-exécution = 0 ligne). Ne touche ni `audit` (triggers `audit_no_update`/`audit_no_delete` intacts : l'audit n'enregistre pas `result_json`, voir `_callback_and_audit`) ni `callbacks`.
- **Pas de migration** : aucun changement de schéma, `SCHEMA_VERSION` reste 2, `PRAGMA user_version` inchangé → trivialement additif et réversible. Si le planner veut tout de même un index, ce serait la migration 3 (`CREATE INDEX`), à éviter ici (mesure DS-PERF-2 : inutile).
- **Après purge** : `GET` renvoie `data: {"purged": true}` ; un rappel déjà final n'est plus envoyé, donc aucune incohérence. Les pages SQLite libérées sont réutilisées mais le fichier ne rétrécit pas (pas de `auto_vacuum`) : le documenter ; `VACUUM` manuel hors périmètre (sauvegarde avant migration = 999.2).
- **CLI** : `cli.py` suit le motif `@app.command()` + `resolve_home()` + `locations.db_path(home)` (`locations.py:34`) ; ouvrir avec `store.connect` (pas `open_db` : ne pas migrer). Le runner peut tourner en même temps (WAL, `BEGIN IMMEDIATE`, `busy_timeout=5000`) ; sur `OperationalError` afficher un message français et sortir en code 1. Sortie : nombre de tâches purgées (stdout).
- Alternative non retenue : stocker `data` dans une colonne dédiée (migration 3 additive `ALTER TABLE jobs ADD COLUMN data_json TEXT`) : résout DS-PERF-1 mais impose de réécrire `finish`/`_terminal`/`claim_due_callback`/`JobRow` ; hors minimum.

**Piège vérifié par sonde locale** : `json.loads('{"a":1e999}', parse_constant=...)` renvoie `{'a': inf}` ; `1e999` ne passe **pas** par `parse_constant` (il passe par `float()`). Il faut `parse_float` qui lève si `not math.isfinite(float(s))`. Avec `parse_float` ajouté, `1e999` est refusé (`refused 1e999`, essai local). `-1e999` pareil. Les entiers énormes (`10**400`) ne produisent pas `inf` (int Python) : sans effet.

Helper unique dans `core/worker_protocol.py` (module pur) :

```python
def _no_constant(name: str) -> object:
    raise ValueError(f"constante JSON non standard : {name}")

def _finite_float(text: str) -> float:
    value = float(text)
    if not math.isfinite(value):
        raise ValueError("flottant hors limites")
    return value

def _loads_strict(raw: bytes) -> object:
    return json.loads(raw, parse_constant=_no_constant, parse_float=_finite_float)
```
`parse_result` et `parse_event` l'appellent ; les `except (ValueError, RecursionError)` existants convertissent en `"invalid"`/`None`. ### Anti-Patterns to Avoid
- **Attraper `Exception` dans le sender sans exclure les erreurs de base** : un `StaleTransition` serait ré-enregistré en boucle, et une `OperationalError` transitoire consommerait des tentatives réelles de la ligne.
- **Se fier à `parse_constant` seul** (voir `1e999`).
- **Deux sources de forme** (rappel et GET construits séparément) : utiliser un helper unique.
- **Interpoler `str(exc)` ou la `resumeUrl` dans le message du sender** (règle 6).
- **Utiliser `json_set` sans filtre `json_type`** : réécrirait des lignes inutilement et pourrait lever sur `result_json` invalide (`json_set` lève « malformed JSON ») ; ajouter `json_valid(result_json)` au `WHERE` si des lignes corrompues sont possibles (c'est précisément le scénario du test P-01 : prévoir `AND json_valid(result_json)`).

## Common Pitfalls

### Pitfall 1 : `1e999` passe `parse_constant`
**Ce qui se passe :** `inf` entre dans la base, le rappel et `GET` (500).
**Évitement :** `parse_float` en plus ; tester `1e999` et `-1e999`.
**Signal :** test `("invalid", None)` rouge sur ce cas seulement.

### Pitfall 2 : l'ordre des clés casse le test de contrat
`tests/unit/test_payload.py:CLES` fige `["job_id","capability","status","duration_s","summary","artifacts","error"]` ; il faut l'inclure `data` après `summary`. Idem tout test d'API qui compare un dictionnaire entier (`tests/fs/test_routes_jobs.py`, `tests/e2e/test_callback_flow.py` à relire).

### Pitfall 3 : `test_succes_sans_data` affirme le contraire du nouveau contrat
`tests/unit/test_payload.py:44-49` (`b'"D"' not in encode(body)`) doit devenir « `data` présent » ; `RESULTAT` contient `"data":{"secret":"D"}` : renommer la valeur (elle s'appelle `secret` mais `data` n'est pas un secret ; ne pas laisser un test qui suggère que `data` est confidentiel). Documenter que **`data` n'est pas masqué par `redact`** (secrets : responsabilité du plugin) ; vérifier que `core/redact` n'est pas appliqué au corps (non, seul `signature`).

### Pitfall 4 : la mesure du repli oublie `data`
Si `build_callback` n'inclut pas `data` au moment de `_cap_result`, un `data` de 1 Mio part en rappel > 1 Mio → 413 → `minimal` (perte de `data` côté n8n). Test : `summary` 600 ko + `data` 600 ko → `data` déporté, `summary` intact.

### Pitfall 5 : rappel `minimal` perd `data` sans le dire
`payload.minimal` doit marquer `data` ; sinon `data` volumineux revient dans le renvoi après 413.

### Pitfall 6 : purge sur ligne à `result_json` invalide
`json_set` lève sur JSON malformé : filtrer par `json_valid(result_json)`, sinon la commande échoue entière sur une seule ligne.

### Pitfall 7 : `fsync` + `os.replace` sous Windows
`_write_summary` n'a pas le `_replace` à réessais du SDK (PermissionError antivirus). Reprendre le motif tel quel pour la cohérence ; ne pas l'améliorer ici.

```python
# engine.py : remplace _cap_summary ; appelé par _evaluate avec summary et data
def _cap_result(self, cur, parsed, result_json: str) -> str:
    def size(rj: str) -> int:
        body = build_callback(job_id=cur.job_id, capability=cur.capability, status=SUCCEEDED,
                              started_at=None, finished_at=None, result_json=rj,
                              error_code=None, error_message=None, max_bytes=None)
        return len(encode(body))
    if size(result_json) <= self._callback_max_bytes:
        return result_json
    result = json.loads(result_json)
    result["data"] = self._offload(cur, "data.json", parsed.data, "data_write_failed")
    rj = json.dumps(result, ensure_ascii=False, allow_nan=False)
    if size(rj) <= self._callback_max_bytes:
        return rj
    result["summary"] = self._offload(cur, "summary.json", parsed.summary, "summary_write_failed")
    return json.dumps(result, ensure_ascii=False, allow_nan=False)
```
