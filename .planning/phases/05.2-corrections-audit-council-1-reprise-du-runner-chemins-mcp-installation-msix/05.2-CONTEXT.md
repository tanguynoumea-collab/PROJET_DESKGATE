## Implementation Decisions

L'utilisateur n'a retenu aucune zone à discuter (2026-10-22) : toutes les décisions ci-dessous sont des choix de Claude, fondés sur le rapport d'audit, l'arbitrage council et les recherches des phases 4 et 5. Elles sont verrouillées pour le planificateur, sauf mention « latitude ».

### Reprise du runner (ARC-001, FIA-001, MNT-007, TST-004, FIA-005, FIA-003)
- **D-01:** L'engine tolère les erreurs SQLite transitoires (`sqlite3.OperationalError` : verrou ou occupation, E/S) pendant le suivi et la réclamation : il journalise, **ne tue pas** le Job en cours, ferme puis rouvre sa connexion et réessaie au tour suivant avec back-off. La tâche continue de tourner. Le seuil fatal est de N erreurs consécutives, comme `MAX_CONSECUTIVE_ERRORS = 5` du sender. Une erreur du plugin reste traitée comme aujourd'hui.
- **D-02:** Un échec fatal d'un thread fait sortir `serve()` avec un **code dédié non nul**, `EXIT_THREAD_FAILED = 6`, à la suite des codes 2 à 5 de `runtime.py`. Le journal dit quel thread est mort et pourquoi. Le commentaire faux de `runtime.py:158` est corrigé.
- **D-03:** La relance ne repose **pas** sur l'hypothèse non prouvée « `RestartOnFailure` relance un code non nul » : la phase 5 a seulement montré qu'il ne relance pas un processus tué (`05-RESEARCH.md`, 140 s d'observation). Ordre de préférence, à trancher par la recherche de phase :
  1. Une expérience jetable montre que `RestartOnFailure` relance bien une action sortie avec un code non nul. Il faut une tâche jetable, jamais la tâche `Deskgate` de l'utilisateur, la créer et la supprimer dans le test, sans élévation. Si c'est prouvé, D-02 suffit et un test `scheduler` réel le fige.
  2. Sinon, **re-supervision dans le processus** : `serve()` ne sort pas. Il recrée le thread mort avec une connexion neuve, après avoir conclu la tâche courante en `interrupted` avec son rappel (même transaction que la recovery existante). Le code non nul de D-02 reste réservé à l'échec répété de cette re-supervision, par exemple 3 recréations en 10 min.
  - Pas d'auto-relance par `schtasks /Run` lancé depuis le runner qui sort : la course avec `MultipleInstancesPolicy IgnoreNew` et le mutex est trop fragile.
  - **Tranché par la recherche (05.2-RESEARCH.md, expérience E1, 2026-10-22) : cas 2.** Une tâche jetable sortie en code 6 n'a été démarrée qu'une fois en 265 s malgré `RestartOnFailure` PT1M×3 (`LastTaskResult` = 6). La re-supervision dans le processus est retenue (superviseur, budget de 3 recréations en 10 min, puis sortie en code 6).
- **D-04:** Test e2e obligatoire : on force la mort d'un thread et on vérifie le code de sortie (cas 1) ou la recréation du thread avec le rappel `interrupted` (cas 2). Le découpage de `serve()` expose une fonction pure de décision (par exemple `exit_code(engine_failed, sender_failed)`), testable sans processus.
- **D-05 (MNT-007):** Le docstring de chaque module (`engine.py`, `sender.py`) justifie en une ou deux phrases sa politique d'erreur après D-01.
- **D-06 (TST-004):** `Engine.stop()` ferme sa connexion paresseuse. Une fois la suite à zéro `ResourceWarning: unclosed database`, `filterwarnings = error::ResourceWarning` est ajouté à pytest.
- **D-07 (FIA-005):** `GET /health` ajoute `engine` et `sender` ∈ {`ok`, `failed`, `stale`}. `stale` vaut quand `last_tick_at` est plus ancien que 10 fois la période de sondage. Le champ `status` passe à `degraded` si l'un n'est pas `ok`. La route reste publique, sans aucun secret ni chemin. `doctor.check_port` lit ces champs. Latitude : noms exacts des champs. **Précisé après recherche (Pitfall 5)** : le seuil `stale` est `max(10 × période, plancher)`, avec un plancher de 30 s pour l'engine et 60 s pour le sender, pour éviter un faux `stale` pendant un POST de rappel de 30 s.
- **D-08 (FIA-003):** Le journal fichier est attaché **avant** `load_config`, puisque le dossier du runner est connu sans la configuration. Un échec de démarrage (configuration invalide, `open_db`, `recover_interrupted`) est journalisé avec sa trace. `serve()` est enveloppé d'un `logger.exception` final. **Révisé après recherche** : un `startup.log` séparé, sans rotation et plafonné, attaché avant le mutex ; `runner.log` (rotatif) reste attaché après le mutex, car un second runner ferait échouer sa rotation sous Windows.

### Chemins des appels MCP (SEC-001, SEC-005)
- **D-09:** La déclaration se fait **par outil**, dans le serveur : `[mcp_servers.X]` gagne `path_arguments = { read_file = ["path"], write_file = ["path"] }`. On ne déclare pas sur la capacité `mcp.call`, qui est partagée par tous les serveurs. Validation au chargement : chaque outil de `path_arguments` figure dans `allowed_tools`, et chaque nom de clé est un identifiant.
- **D-10:** Seules les clés de **premier niveau** de `arguments` sont visées, avec les mêmes types de valeur que les `path_params` des plugins python. Elles passent par `convert_path_params` / `validate_container_path` (`src/deskgate/core/paths.py:162-181`) à la soumission (refus 422, codes `path_outside_roots` / `path_invalid`) **et** au lancement : même double validation que pour `kind = "python"`. La valeur transmise au serveur est le chemin hôte converti et résolu.
- **D-11:** Les arguments non déclarés restent **opaques**, sans heuristique de détection de chemins. La règle est documentée noir sur blanc :
  - dans `src/deskgate/runner.example.toml`, section MCP : « seuls les arguments de `path_arguments` sont convertis et validés ; n'autorisez pas d'outil de fichiers sans les déclarer » ;
  - dans `ARCHITECTURE.md` §7, en corrigeant la promesse de la ligne 108.
- **D-12:** Tests obligatoires pour `mcp.call`, sur le mini-serveur MCP de test (D-12 de la phase 4) avec un outil de fichiers de test : refus `..`, refus par jonction, refus par lien (sauté sans privilège comme ailleurs), conversion `/data/...` vers l'hôte, et refus d'un argument déclaré hors racine dès la soumission.
- **D-13 (SEC-005):** L'engine n'injecte dans le worker que les variables `DESKGATE_MCPENV__<SERVEUR>__*` du serveur visé (`params.server`, connu au lancement). Si le serveur est inconnu au lancement, rien n'est injecté et le worker échoue déjà proprement (`server_not_declared`).

### Installation MSIX (LIV-001)
- **D-14 (révisé après recherche, expérience E3) :** l'API seule ne suffit pas. Dans cette session Claude, dont les écritures sont pourtant virtualisées, `GetCurrentPackageFullName` renvoie 15700 (« pas empaqueté ») et le chemin vu reste le chemin normal. La détection principale est donc une **sonde d'écriture** : un marqueur unique écrit sous `%LOCALAPPDATA%`, puis recherché sous `%LOCALAPPDATA%\Packages\*\LocalCache\Local\` ; les deux copies sont nettoyées. `GetCurrentPackageFullName` reste un signal complémentaire pour les processus qui portent une identité de paquet. Le code vit dans `scheduler.py`, déjà autorisé à importer `ctypes` et `subprocess`. `init` détecte **avant toute écriture**.
- **D-15:** `deskgate init` **refuse** dans un contexte empaqueté : message en français qui renvoie vers « Terminal normal obligatoire » d'`AGENTS.md`, et code de sortie non nul. Pas de contournement par `--force`, car l'installation obtenue ne peut pas fonctionner. `deskgate doctor` ajoute un contrôle « Contexte d'exécution » en `echec` dans ce cas.
- **D-16:** `deskgate doctor` lit le **dernier résultat** de la tâche planifiée et signale `0x8007010B` comme échec, avec la cause probable (installation virtualisée). Il signale aussi tout autre code d'échec en avertissement. Les codes « tâche en cours » et « jamais exécutée » ne sont pas des échecs. Latitude pour la source : `schtasks /query /v /fo csv` dépend de la langue de Windows (colonnes en français), donc on préfère une source indépendante de la langue (COM `Schedule.Service` via ctypes interdit par la pile, `Get-ScheduledTaskInfo` ou équivalent). La recherche tranche, sans ajouter de dépendance.

### Diagnostic générique des plugins (PER-001)
- **D-17:** `doctor.py` ne connaît plus `bcf_executable`. Une capacité `kind = "python"` peut déclarer `required_files = ["bcf_executable"]` : noms de clés de `settings` dont la valeur doit être un fichier existant. `doctor` vérifie ces clés génériquement. `runner.example.toml` (exemple `ifc.clash`) et la documentation d'installation déclarent `required_files`. Le cœur reste ignorant du BIM (règle 1). Pas de migration de configuration : le projet n'a pas d'utilisateur.
