### Pattern 1 : erreurs transitoires de l'engine avec conclusions différées (D-01, ARC-001/FIA-001)

Constat dans le code (`engine.py`) : `tick()` ouvre la connexion et appelle `claim_next`, `is_cancel_requested`, `update_progress`, `finish`. Toute `OperationalError` remonte jusqu'à `run()` qui pose `failed = True` et sort. Pire : `_observe` attrape `Exception`, **tue le Job** (`cur.job.terminate`), puis `_fail(conn, ...)` retouche la base, ce qui relance l'exception ; et `_conclude` libère `_cur` dans un `finally` même si `store.finish` a échoué, ce qui laisse la ligne `running` sans suivi et bloque la ressource.

Conception :
- `store.py` expose `OperationalError = sqlite3.OperationalError` (alias comme `Connection`) : `engine.py` n'importe pas `sqlite3` (test d'architecture).
- `run()` : boucle `try: self.tick(); errors = 0` / `except store.OperationalError:` journaliser (`logger.warning` sans trace répétée, une trace à la première et à la dernière), `errors += 1`, fermer la connexion (`_drop_connection`), si `errors >= MAX_DB_ERRORS` (5) relancer l'exception (chemin fatal existant), sinon `self._stop.wait(min(30, 2**errors))`. Même schéma que `Sender.run`.
- `_observe` : ajouter `except store.OperationalError: raise` **avant** `except Exception` : le Job continue de tourner.
- `_launch` : même clause ; la ligne a déjà été réclamée (`running`).
- Conclusion différée : `_conclude` et `_fail` ne doivent pas perdre le verdict. Mémoriser `self._unsettled: tuple[str, Verdict, str | None] | None` (ou l'attacher à `_Running` : `cur.pending`) quand `store.finish` lève une `OperationalError`, **ne pas** libérer `_cur`, et rejouer en tête du tour suivant (transition gardée par `from_status=RUNNING` + `StaleTransition`, donc idempotente).
- Seuil fatal : le thread meurt avec `failed = True` ; c'est ensuite le superviseur qui conclut la tâche en `interrupted` (voir Pattern 2).
- Erreurs non transitoires (`sqlite3.DatabaseError` autre que `OperationalError`, `RuntimeError` d'invariant) : comportement actuel (fatal immédiat). Erreur du plugin : inchangée.

### Pattern 2 : superviseur dans le processus (D-03 cas 2, D-02, D-04)

`serve()` bloque aujourd'hui dans `server.run(...)` ; `on_fatal` ne fait que `server.should_exit = True` puis `serve` renvoie **0** (`return 0`, commentaire faux « Le Planificateur relancera le runner »). Nouveau découpage :

```python
# supervisor.py : aucune importation de sqlite3 ni de ctypes
EXIT_THREAD_FAILED = 6          # ou dans runtime.py avec les autres codes
MAX_RESTARTS = 3
WINDOW_S = 600.0

@dataclass(frozen=True)
class Decision:
    restart_engine: bool
    restart_sender: bool
    give_up: bool

def decide(*, engine_failed: bool, sender_failed: bool,
           recent_restarts: int, max_restarts: int = MAX_RESTARTS) -> Decision:
    """Fonction pure : que faire de l'état observé. Testée sans processus ni thread."""
    if not (engine_failed or sender_failed):
        return Decision(False, False, False)
    needed = int(engine_failed) + int(sender_failed)
    if recent_restarts + needed > max_restarts:
        return Decision(False, False, True)
    return Decision(engine_failed, sender_failed, False)

def exit_code(*, gave_up: bool) -> int:
    return EXIT_THREAD_FAILED if gave_up else 0
```
(le budget compte les recréations dans la fenêtre glissante : liste d'horodatages purgée par une seconde fonction pure `recent(times, now, window)`.)

`Supervisor` : thread `deskgate-supervisor`, `threading.Event` posé par les `on_fatal` des deux threads (réveil immédiat) avec attente périodique de 1 s en filet. Il porte un `holder` (`engine`, `sender` courants) lu par les routes et par `JobsService.wake` (`wake=lambda: holder.engine.wake()` : le `wake=engine.wake` actuel de `runtime.py` serait lié à l'ancien objet).

Séquence de reprise du thread engine :
1. `old.stop()` : tue le Job tenu par le thread mort (`cur.job.terminate`, `close`) et ferme `_conn` (D-06). Le thread est mort (`failed` est posé avant `finally`), pas de course sur le Job.
2. `ids = recover()` avec **connexion neuve** : `store.connect` + `store.recover_interrupted` (une transaction : `running → interrupted` + rappel `pending` + audit). Fermer la connexion. Si cette étape lève (base indisponible), compter un échec et réessayer au tour suivant dans le budget.
3. `new = make_engine()`, `new.on_fatal = supervisor.notify`, `new.start()`, `holder.engine = new`, `sender.wake()`.
Reprise du sender : `old.stop()` (ferme client HTTP et connexion), `make_sender()` (nouveau `httpx2.Client`), `start()`. Les rappels `pending` sont dans la base ; l'écriture préalable de l'essai (`claim_due_callback`) et `maybe_delivered` couvrent un envoi interrompu.
Abandon : au-delà du budget (ou exception dans la reprise elle-même), `server.should_exit = True`, `gave_up = True`, journal explicite (quel thread, combien de fois, dernière cause) et `serve()` renvoie `exit_code(gave_up=True)` = 6.
Arrêt propre : `_shutdown` (lifespan) et le `finally` de `serve` doivent d'abord `supervisor.stop()` (et joindre) **avant** `engine.stop()` / `sender.stop()` des objets courants, sinon le superviseur recrée un thread pendant l'arrêt.

Choix à figer par le planificateur : le code d'erreur du rappel après reprise reste `runner_restarted` (message « Runner redémarré pendant l'exécution »), seul code documenté dans le workflow n8n d'exemple. Variante possible : paramètre `reason` de `recover_interrupted` (défaut inchangé) si l'on veut un message distinct dans le journal.

Ne couvre pas : un thread **bloqué** (non mort). C'est le rôle de l'état `stale` de `/health` (D-07), sans recréation automatique en 5.2 (à signaler comme limite connue dans le docstring).

### Pattern 3 : `path_arguments` par outil (D-09, D-10, D-13)

État actuel (lu dans le code) :
- Soumission : `jobs.JobsService.submit` appelle `convert_path_params(req.params, cap.path_params, ...)` ; pour `kind = "mcp"`, `cap.path_params` est toujours vide (validateur `mcp_fields_forbidden`) : aucune validation.
- Lancement : `Engine._launch_inner` reconvertit avec `cap.path_params` ; même vide pour MCP.
- Les `params` d'une tâche `mcp.call` sont `{"server", "tool", "arguments": {...}, "call_timeout_s"?}` : `server`, `tool` et `arguments` sont **connus dès la soumission** (ils sont dans le corps de la requête). Le worker (`workers/mcp_call.py`, `_validate`/`_call`) transmet `arguments` tels quels à `client.call_tool`.
- L'injection d'env : `Engine._launch_inner` (l. 257-261) construit `extra_env` pour **tous** les serveurs.

Conception :
- `core/config.py` : `McpServer.path_arguments: dict[ToolName, list[Ident]] = {}` (clé = nom d'outil, mêmes contraintes que `allowed_tools` : 1 à 128 caractères ; valeurs = noms d'arguments `Ident`). `model_validator(mode="after")` : chaque clé figure dans `allowed_tools` (`PydanticCustomError("path_arguments_tool_not_allowed", ...)`). Listes vides refusées ou ignorées (au choix, tester).
- `core/paths.py` (noyau pur, aucune importation interdite) : fonction pure
  ```python
  def convert_mcp_arguments(params, servers, mappings, roots, resolver=default_resolver) -> dict[str, object]:
      """Si params['server'] est déclaré et params['tool'] a des path_arguments, convertit
      params['arguments'] (premier niveau) via convert_path_params ; sinon renvoie params tel quel."""
  ```
  Ne lève rien pour un serveur/outil inconnu ou des `arguments` non objet (le worker produit déjà `server_not_declared`, `tool_not_allowed`, `invalid_params`). Réutilise `convert_path_params` : types acceptés = chaîne ou liste de chaînes, sinon `PathDenied(path_invalid)`.
- `jobs.submit` : si `cap.kind == "mcp"`, appeler `convert_mcp_arguments` (résultat ignoré, la base garde l'original, comme pour python) ; `PathDenied` → `_refuse(exc.code, ...)` + 422, même bloc d'erreur que l'existant.
- `Engine._launch_inner` : pour `kind == "mcp"`, `params = convert_mcp_arguments(...)` (au lieu de `convert_path_params(..., cap.path_params, ...)` qui est un no-op), `PathDenied` → `_fail(...)` avec `exc.code` : même double validation que python. L'ordre actuel (conversion avant la branche) est à scinder : branche `mcp` calcule `params` et `extra_env`.
- D-13 : `server = params.get("server")` ; `extra_env` = uniquement `mcp_env_var(server, key)` pour `servers[server].env` si `server` est une chaîne déclarée, sinon `{}`. Option cohérente de durcissement (non demandée) : ne mettre dans `settings["servers"]` que le serveur visé, le worker n'a besoin que de celui-là ; à ne faire que si les tests existants (`test_engine_launch_params.py`) sont adaptés.
- Risque connu à documenter (D-11) : `..` dans une valeur non déclarée, ou un chemin dans un argument imbriqué, reste opaque. Une fois les chemins convertis, la valeur transmise est un chemin hôte absolu : l'outil du serveur MCP peut ensuite sortir des racines (symlink créé après validation) : fenêtre TOCTOU identique à celle des plugins python, hors périmètre.

### Pattern 5 : dernier résultat de la tâche (D-16)

```python
def last_task_result(name: str = TASK_NAME) -> int | None:
    # name validé par ^[A-Za-z0-9._-]+$ ; argv fixe, aucun shell
    ps = os.path.join(SYSTEMROOT, "System32", "WindowsPowerShell", "v1.0", "powershell.exe")
    cmd = [ps, "-NoProfile", "-NonInteractive", "-Command",
           f"(Get-ScheduledTaskInfo -TaskName '{name}').LastTaskResult"]
    res = subprocess.run(cmd, capture_output=True, text=True, timeout=20, check=False,
                         creationflags=subprocess.CREATE_NO_WINDOW)
    try: return int(res.stdout.strip()) & 0xFFFFFFFF
    except ValueError: return None
```
Pure : `classify_task_result(code) -> "ok" | "running" | "never" | "virtualized" | "runner_exit" | "failure"`.
- `0` ok ; `0x41301` en cours ; `0x41303` jamais exécutée ; toute valeur `0x00041300-0x0004131F` (famille `SCHED_S_*`) : pas un échec ; `0x8007010B` → échec, cause probable « installation virtualisée par une application MSIX (dossier de travail inexistant pour le Planificateur) : refaire depuis un terminal normal » ; `2..6` : codes de sortie du runner (`EXIT_*`) → avertissement avec la signification (2 configuration invalide, 3 déjà en cours, 4 port, 5 base, 6 thread fatal) ; autre → avertissement « code 0x… ».
- `None` (PowerShell absent/erreur) : avertissement « dernier résultat illisible » (ne jamais en faire un échec).
- Intégration : `check_task` appelle `last_task_result` après l'audit XML, injectable comme `query` (`Callable[[str], int | None]`) pour les tests unitaires.

### Pattern 6 : `/health` et diagnostic (D-07)

- `Engine.status(now)` et `Sender.status(now)` → `"ok" | "failed" | "stale"` (fonction pure `thread_state(failed, age_s, poll_s, factor=10)` dans le noyau ou `supervisor.py`). L'`age` de l'engine est un `monotonic` (float), celui du sender un `datetime` : uniformiser dans la fonction pure.
- `create_app(..., threads: Callable[[], Mapping[str, str]] | None = None)` → `app.state.threads` ; `/health` renvoie `{"status": "ok"|"degraded", "version", "warnings", "engine", "sender"}`. Aucun chemin, aucun secret (le test e2e `test_health_sans_jeton` vérifie l'absence de `:\\`, `:/`, `token` ; il vérifie aussi `set(body) == {"status", "version", "warnings"}` : **à mettre à jour**).
- `doctor.check_port` : aujourd'hui le succès exige `body.get("status") == "ok"`, sinon il retombe sur le test de liaison et conclut « port occupé par un autre programme » ; avec `degraded` ce serait un faux diagnostic. Lire `status`/`engine`/`sender` : `ok` → ok ; `degraded` → `echec` « runner joignable mais thread X en état Y ».

### Pattern 7 : `required_files` (D-17, PER-001)

- `Capability.required_files: list[Ident] = []`. Validateur `after` : (a) interdit pour `kind = "mcp"` (ajouter à la liste de `mcp_fields_forbidden`) ; (b) chaque nom est une clé de `settings` (`PydanticCustomError("required_file_not_in_settings")`) ; (c) la valeur correspondante est une chaîne non vide (`required_file_not_a_string`). L'existence du fichier n'est **pas** vérifiée au chargement (`load_config` ne touche pas le disque, et le test de config reste pur) : c'est le rôle de `doctor`.
- `doctor.check_plugins` (l. 105-130) : supprimer le bloc `bcf_executable` ; pour chaque capacité `python`, `for key in cap.required_files: Path(str(cap.settings[key])).is_file()` sinon `echec` `"{ident} : {key} absent ({valeur})"`. Le test `tests/unit/test_doctor.py::test_plugins_bcf_executable_absent` (l. 146) doit être réécrit avec `required_files`. Aucune migration (D-17).
- `runner.example.toml` (bloc `ifc.clash`, l. 55-69) : ajouter `required_files = ["bcf_executable"]` ; `tests/unit/test_runner_example.py` (marqueurs `>>> / <<< exemples phase 4`) et `tests/unit/test_init.py:57` doivent rester verts ; la documentation d'installation (`AGENTS.md` § 4, l. 114 et suivantes) et `plugins/bim/README.md` mentionnent la clé. Le plugin BIM continue de lire `settings.bcf_executable` lui-même (`bcfjob.py`).

### Pattern 8 : journal de démarrage (D-08, FIA-003)

`runtime.serve()` : le journal fichier est attaché après le mutex pour une bonne raison (rotation de `RotatingFileHandler` sous Windows : un second processus qui tient le même fichier ouvert fait échouer le `rollover` avec `PermissionError`). Attacher `runner.log` **avant** `load_config` rouvrirait ce risque pour un second runner qui sortirait en code 3. Recommandation (latitude D-08) : un fichier **distinct** `logs\startup.log`, `FileHandler` en ajout sans rotation, plafonné (tronquer au-delà de 256 Kio avant ouverture), attaché dès que `resolve_home()` est connu (avant `load_config`) ; il reçoit les erreurs de configuration, de mutex, de liaison, de base, et le `logger.exception` final. `_err()` écrit aussi dans le logger. Une fois le mutex acquis, `runner.log` reste attaché comme aujourd'hui. `serve()` devient un enrobage : `try: return _serve(...) except Exception: logger.exception("Échec fatal du runner."); raise` (code de sortie 1 naturel, trace sur stderr en console). `locations.py` gagne `startup_log_path(home)` ; `check_config` du doctor cite `startup.log` dans `_CONSOLE_HINT`.

### Anti-Patterns to Avoid
- **Se fier à `GetCurrentPackageFullName` seule** (E3) ou au seul chemin résolu : ne détectent pas LIV-001 dans cette session.
- **Analyser le texte ou le CSV de `schtasks`** : localisé (règle déjà écrite dans `scheduler.py`).
- **Fermer `sqlite3.Connection` depuis un autre thread** : `connect` n'utilise pas `check_same_thread=False`. `Engine.stop()` ne ferme `_conn` que si le thread est mort ou jamais démarré (voir Pitfall 4).
- **Recréer le thread engine sans avoir conclu le Job** : la ressource resterait occupée et le plugin continuerait dans un Job orphelin.
- **Relancer par `schtasks /Run` depuis le runner** : écarté par D-03.
- **Ajouter `psutil`, `pywin32` ou une dépendance** : inutile ici.

## Don't Hand-Roll

| Problème | Ne pas construire | Utiliser | Pourquoi |
|---|---|---|---|
| Conversion/validation des chemins MCP | Un second validateur de chemins | `convert_path_params` / `validate_container_path` | Jonctions, liens, `..`, UNC, ADS déjà traités et testés |
| Passage `running → interrupted` + rappel | Un UPDATE spécifique au superviseur | `store.recover_interrupted` | Une transaction, audit et rappel inclus |
| Back-off des erreurs | Un nouveau mécanisme | Le modèle de `Sender.run` (`min(30, 2**errors)`, seuil 5) | Cohérence, tests existants |
| Dernier résultat de tâche | Analyse de `schtasks` ou COM | `Get-ScheduledTaskInfo` (argv fixe) | Valeur numérique indépendante de la langue |
| Serveur MCP de test | Un second serveur | `tests/mcp_fake/mini_server.py` + un outil `read_file`/`write_file` | Déjà branché (`_support/mcp_env.py`) |
| Faux threads morts | Mocks de `threading` | Engine/Sender réels avec `tick` patché, ou fabriques injectées au `Supervisor` | Plus fidèle, déterministe |

**Key insight :** tout le comportement « difficile » existe déjà (recovery transactionnelle, validation de chemins, back-off) ; la phase consiste à le **brancher** aux bons endroits et à le **prouver** par des tests qui tuent vraiment un thread ou une tâche.

## Common Pitfalls

### Pitfall 1 : croire que le code de sortie 6 relance le runner
**What goes wrong:** D-02 seule laisse le runner arrêté jusqu'à la prochaine ouverture de session. **Why:** E1 (aucune relance sur code 6). **How to avoid:** superviseur (Pattern 2) ; le test `scheduler` ne doit PAS affirmer une relance. **Warning signs:** un test qui compte des démarrages après une sortie non nulle.

### Pitfall 2 : `on_fatal` appelé depuis le thread mort qui est ensuite joint
`Engine.stop()` fait `thread.join(timeout)` : sur un thread déjà terminé c'est immédiat, mais appelé **depuis** `on_fatal` (donc depuis le thread mourant) ce serait un auto-join (`RuntimeError`). Le superviseur doit s'exécuter dans son propre thread, jamais dans le rappel `on_fatal` (qui ne fait que poser un `Event`).

### Pitfall 3 : sonde d'écriture et nettoyage
La suppression du marqueur dans la vue fusionnée peut laisser la copie physique sous `Packages\...\LocalCache\Local\`. Après `unlink`, supprimer aussi les copies trouvées par le `glob` (suppress `OSError`). Le nom contient un `uuid` : aucun risque de collision. Ne rien écrire hors de `%LOCALAPPDATA%` direct.

### Pitfall 4 : `Engine.stop()` et sa connexion (D-06)
`stop()` ferme déjà `_conn` indirectement via `run()` (bloc `finally`) quand le thread a tourné ; les ~187 `ResourceWarning` viennent des tests qui appellent `tick()` sans thread (`_conn` ouverte, jamais fermée). Fermer dans `stop()` **après** le `join` et seulement si `thread is None or not thread.is_alive()`. Ne pas activer `filterwarnings = error::ResourceWarning` avant que la suite soit à zéro (le faire dans la dernière tâche du plan, après un run complet), et traiter aussi les `Sender` de test et les `store.connect` oubliés dans `tests/_support`.

### Pitfall 5 : faux « stale » (D-07)
`Sender.last_tick_at` est posé au début d'un tour ; un POST peut durer jusqu'à `read=30 s` (Timeout 10/30). Avec la période de sondage de 1 s, « 10 × période » = 10 s déclarerait `stale` un sender sain pendant un envoi lent. De même `Engine._reap` attend jusqu'à `WAIT_AFTER_KILL_S = 5 s`. Recommandation : seuil `max(10 × poll, 60 s)` pour le sender et `max(10 × poll, 30 s)` pour l'engine, ou mettre `last_tick_at` à jour aussi en fin de tour. Le texte de D-07 (« 10 fois la période ») est respecté comme plancher ; tester les deux bornes avec des horloges injectées.

### Pitfall 6 : `check_port` sur `degraded`
Voir Pattern 6 : sans modification, un runner dégradé est diagnostiqué « port occupé ». Prévoir le test.

### Pitfall 7 : test e2e de mort de thread sans crochet de production
N'ajouter aucun crochet de panne dans le code de production. Le test e2e lance un petit script pilote (`tests/_support/serve_with_fault.py`) qui importe `deskgate.runtime`, remplace `Engine.tick` par une fonction qui lève après N appels (ou `store.claim_next`), puis appelle `runtime.serve()` : le runner reste un vrai sous-processus. Le script pilote est du code de test, hors `src/`.

### Pitfall 8 : `init` qui écrit avant de refuser
`init_config` crée `home`, les dossiers et `runner.toml` : la détection doit précéder tout cela ; le test vérifie qu'aucun fichier n'est créé dans `home` ni sous la racine.

### Pitfall 9 : `startup.log` partagé entre deux runners
Voir Pattern 8 : ne pas attacher `RotatingFileHandler` avant le mutex.

### Pitfall 10 : `McpServer.path_arguments` et clés d'outils
Les noms d'outils MCP peuvent contenir `-`, `.` : ne pas leur appliquer le motif `Ident`. Seuls les **noms d'arguments** sont des identifiants. Un `dict[Ident, ...]` pour les outils rejetterait des outils légitimes.

### Conversion des arguments MCP (D-10)
```python
# core/paths.py
def convert_mcp_arguments(params, servers, mappings, roots, resolver=default_resolver):
    server = servers.get(params.get("server")) if isinstance(params.get("server"), str) else None
    tool = params.get("tool")
    args = params.get("arguments")
    if server is None or not isinstance(tool, str) or not isinstance(args, dict):
        return dict(params)
    keys = server.path_arguments.get(tool, [])
    if not keys:
        return dict(params)
    out = dict(params)
    out["arguments"] = convert_path_params(args, keys, mappings, roots, resolver)
    return out
```

## Open Questions

1. **Message d'erreur du rappel après reprise d'un thread engine mort**
   - Connu : `recover_interrupted` écrit `runner_restarted` / « Runner redémarré pendant l'exécution ».
   - Flou : le runner n'a pas redémarré, seul l'engine a été recréé.
   - Recommandation : garder le code `runner_restarted` (contrat n8n unique) ; ajouter, si souhaité, un paramètre `message` optionnel. Décision du planificateur, réversible.
2. **Détection par ancêtres (`WindowsApps`)**
   - Connu : la chaîne de processus montre `claude.exe` sous `C:\Program Files\WindowsApps\Claude_...`.
   - Flou : coût (Toolhelp par ctypes) pour peu de gain par rapport à la sonde d'écriture ; un ancêtre déjà sorti n'apparaît plus.
   - Recommandation : ne pas l'implémenter en 5.2 ; la sonde suffit.
3. **Terminal Windows Store (paquet MSIX) et ses shells**
   - Non testé : les shells enfants de Windows Terminal ne sont pas virtualisés d'ordinaire ; si c'était le cas, la sonde les détecte aussi (comportement voulu).
4. **Autre code que 6 sous `RestartOnFailure`** : non testé (LOW) ; l'absence de relance a été observée pour un `LastTaskResult` non nul quelconque, la conclusion tient.
5. **Hang d'un thread (stale)** : pas de recréation automatique en 5.2 (signalé seulement).
